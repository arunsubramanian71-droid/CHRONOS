# Deviations, interpretations and open questions

This is the project's decision log for everything where the implementation **interprets**, **extends** or **departs from**
`CHRONOS System Specification v0.2.pdf`, plus the specification's own open questions. The specification says that after
confirmation a decision changes only by adding a new decision that supersedes it, with the consequences written down; the entries
below follow that rule. Nothing here changes the approved decisions D-01 to D-26: they are implemented, and where an
implementation choice was needed it is recorded here.

## Interpretations of an underspecified rule

| ID | Specification text | What was done and why |
|---|---|---|
| DEV-01 | Event-kind rank in the tie-break key is not defined. | `FAULT 0 < CLIENT_INPUT 1 < DELIVERY 2 < TIMER 3` (`AgendaItem.Kind`). A message arriving at the same instant as a timer is delivered first. This matters for AD-4: with constant latency and a 300 ms watchdog, healing the partition 200 ms earlier makes the heartbeat arrive exactly when the watchdog is due, and delivery-before-timer is what lets it cancel the watchdog. Deterministic, documented, and tested. |
| DEV-02 | Content digest = "node, kind, canonical payload, **parent ids**, origin, state digest". | Parent ids in the digest **exclude PROGRAM_ORDER links** (`Event.contentDigest`). For node events they are implied by the per-node counter; for env events (identity-keyed, D-24) they would make every env event depend on which unrelated env events preceded it, which produces false `Changed` events and spurious causal roots. |
| DEV-03 | Phase 12a: a fault "touches" a node if the node sits on a side of an active partition that cuts it off from another node. | **CLOSED (2026-10-20): final scope = "evidence scope".** A partition touches a node on one of its sides when (a) the node has received a message from a node on the other side before (the test the specification prescribes for crash and pause in 12b), **or** (b) the partition dropped a message addressed to that node at or after the timer was set (`FaultInjector.silencedDuring`, `ActiveFault.lastDropTo`, part of the world image). It is a subset of the specification's literal 12a sentence in every case and a superset of the earlier heard-from scope. **Why this and not either extreme.** *Literal* gives OMISSION edges to timers that wait for nothing across the cut: in RE four of its five edges were p's own heartbeat timers, the comparison reports p as affected and the divergence cone grows (13 to 17 events), and `why` claims "the timer fired because expected messages never came" for a timer that fires regardless. *Heard-from only* (the scope used until now) had the opposite defect, found while closing this item: a partition that begins before the first contact (`partition:0:500`) left b's watchdog without an OMISSION edge, so `why` could not name the partition at all. The evidence scope keeps the precision (p's heartbeat timers get no edge in RE) and removes the gap (a silenced message is exactly what the edge stands for). The edge stays *potential*. **Evidence:** `OmissionScopeStudyTest` (RE: 1 edge on b, literal 5; early partition: b only, `why` names the partition and says POTENTIAL; resume from every checkpoint; over 240 chaos runs the final scope's edges are always a subset of the literal rule's), `FaultCatalogueTest`, `KnownAnswerTest`, the goldens (unchanged: no existing golden depends on the new case), and the M10, fuzz and soak campaigns re-run on the new scope (`IMPLEMENTATION_STATUS.md`). The literal rule remains available as `--param omission=literal` (recorded in the header) for comparison. **A consequence handled in the comparator:** an OMISSION edge now depends on which messages were dropped, so a branch can lack an edge the baseline has although the event behaved identically; such a root is reported as displaced, reason `potential-edge` (DEV-54). |
| DEV-04 | "Partition ... every message between them is discarded" | Applied **at delivery time** (step-cycle step 3: the fault injector transforms the item when it is taken from the agenda), not at send time. |
| DEV-05 | Section 10 ping-pong table and the step cycle. | To reproduce the table exactly (seq 1 is `B#1`, before `A#2`), `boot()` records the `NODE_STARTED` event of every node first and only then the effects of the start handlers. `stateAfter` of `NODE_STARTED` is the state *after* `onStart` (the specification's "initial state digest"). |
| DEV-06 | FR-01 lists start, message and timer handlers. | The Node API also has `onClientInput` (the CLIENT_INPUT event needs a handler) and `onRestart` (Phase 12b recovery). |
| DEV-07 | Step cycle: events appended as one group (step 8), invariants checked (step 9). | The `INVARIANT_VIOLATED` event is appended **in the same atomic group** as the step that caused it, and is recorded when a violation *begins* (edge-triggered) so a persisting violation does not flood the log. |
| DEV-08 | `DIFFERENT_FAILURE`: "a different invariant was violated, or the violation has a different causal origin". | Simplified: a different invariant name, or a different **set of fields read** by the violated invariant. KA-4 requires `FAILURE_PERSISTS` when either of two independent partitions is removed; a causal-origin test based on the fault source would report `DIFFERENT_FAILURE` there. |
| DEV-09 | Section 20 step 8 path costs. | Ties between equally cheap paths prefer the path with **fewer PROGRAM_ORDER hops**, then the earlier parent (`CausalGraph.path`). Without this the explanation path could consist of a bare env program-order link instead of the OMISSION chain. Found by the anchor-rule test. |
| DEV-10 | D-16 anchor rule when no earlier Same event exists on the root's node. | Falls back to the earliest root of the failure timeline that reaches the failure, and says so in the report (`pathNote`). The flagship demo branches *at the partition's injection boundary* so the anchor (the partition event) exists, which is the reading of AD-5 that matches Section 20's own example. AD-4's wording "branch before the partition" and AD-5's "names the partition event" are not both achievable with an env-only intervention before the partition; this is noted, not hidden. |

## Extensions beyond the text

| ID | Extension | Reason |
|---|---|---|
| DEV-11 | **Heal-enabled FAULT edge.** A delivery of a message that was sent while a partition cut its link, and delivered only after the partition healed, gets a FAULT parent from the `FAULT_CLEARED` event. | Without it, the branch-side event "the heartbeat got through because the heal happened" has no causal link to the intervention that moved the heal, so law M10 ("every root lies in the intervention's causal future") could not hold for the flagship run. |
| DEV-12 | Env identity of repeated copies: `dup:<id>`, `dup:<id>~2`, ...; `drop:<id>~dup`, `drop:<id>~dup2`. | D-24 lists four env id forms; duplicating a message more than once (two rules, or a rule and an intervention) needs a unique identity per copy. Found by the 10,000-seed chaos soak (a real defect: duplicate ids). |
| DEV-13 | The verifier runs a replay to the same end as the original, including trailing steps that recorded nothing. | Found by the chaos soak: a restart rule for a node that was not crashed advances virtual time without an event, so comparing end states at the last event gave a false mismatch. Any event produced by a trailing step is a genuine mismatch. |
| DEV-14 | `CounterfactualEngine.findCriticalFaultSets` removes every single fault rule, then every pair, and lists the minimal critical sets. | Bounded form of Phase 14b "KA-4 reports FAILURE_PERSISTS and lists both causes". It searches over **fault rules**, not over every event of the causal past, so FR-38 (intervention search, Stretch) is still not implemented. |

## Semantics chosen for the fault and intervention catalogue (added after the first delivery)

| ID | Choice |
|---|---|
| DEV-21 | **A checkpoint remembers that its run stopped.** A resumed verification replay from the final checkpoint of a run that stopped on a violation used to continue past the end of the recording (found by testing replay from every checkpoint). The image now records the pending stop and `ReplayEngine` restores it for verification; **branching deliberately does not**, so going live from the end of a stopped timeline continues. |
| DEV-22 | **PAUSE** holds a frozen node's agenda items (deliveries, timers, inputs) until it resumes and runs them then, in their stable order; the resume item is ordered with the node's own items so it precedes them. A crash ends a pause. The OMISSION scope for pause is the crash scope (the node waiting must have heard from the paused one). |
| DEV-23 | **CLOCK_SKEW** changes only `NodeContext.now()`; recorded virtual times and the logical clocks do not change (tested: Lamport and vector values are identical with and without skew). It records a FAULT event but no causal edge, because the engine cannot know which later events *read* the clock. |
| DEV-24 | **SLOW_LINK** is a persistent, link-wide DELAY: deliveries take `factor` times their latency, implemented as extra delay after the recorded latency (so replay stays exact), and each affected delivery has the fault as a FAULT parent. |
| DEV-25 | **REORDER** (`ON_NTH_MESSAGE`) swaps the n-th and the (n+1)-th message of a link: the n-th is held until just after the (n+1)-th; the held delivery carries the reorder fault as a FAULT parent. If the n-th has already been delivered, nothing happens and nothing is recorded. |
| DEV-26 | **AFTER_EVENT trigger** fires a time-triggered action immediately after the named event is recorded (the fault's parent is that event). "On node state" (Stretch) is not implemented. |
| DEV-27 | **PATCH_STATE** (the one synthetic intervention) carries the node's new state in the `INTERVENTION_APPLIED` event itself, becomes the last writer of the field (so it is a WITNESS of a violation it causes), and marks the timeline and all its descendants synthetic (`TimelineManager.isSynthetic`; reports say so). |
| DEV-28 | **Lengthening a partition** (`SHIFT_HEAL` with a positive shift): the extra drops get a FAULT edge from the intervention and its origin; timer firings whose OMISSION edges differ because the fault window moved get a FAULT edge from the intervention (DEV-43). *History: before DEV-43 a branch root could remain outside the intervention's causal future.* |
| DEV-29 | **CONFIG_PATCH** and **RESEED_STREAM** change behaviour from the branch point on. *History: they had no causal link from the intervention.* Now (DEV-43) a handler that reads a patched key links what it does afterwards (sends, timers, draws, notes) to the intervention by FAULT edges, and a draw from a reseeded stream links the draw; the trigger event of that step and the node's state change are not re-linked (events are immutable once built). |
| DEV-30 | **Intervention search (FR-38)** is a bounded, single-change but-for search: suspects are the message sends whose delivery is in the causal past (tried as DROP), scripted client inputs (REMOVE_INPUT) and fault rules (REMOVE_FAULT) in the causal past of the first violation, capped at 64 (those causally closest are kept). It cannot find a cause that needs two changes (KA-4: use `chronos causes`) and does not propose delays, reorderings or other interventions. Every finding is a real counterfactual branch, not an estimate. |
| DEV-31 | **Consistent cuts and the knowledge view.** A cut is consistent when it is closed under every parent edge (PROGRAM_ORDER, STEP_EFFECT, MESSAGE, TIMER, FAULT, WITNESS, OMISSION), which equals closure under happens-before (the graph self-check). The knowledge view defines "what A has heard about B at event e" as B's last event in the causal past of e; the state it prints as "believes" is B's recorded state as of that event, which is a reconstruction from the log, not a value any node stored. |
| DEV-32 | **Node-local replay (R5)** feeds one node its recorded inputs (start, restart, crash, delivered messages with the recorded body, timer firings, client inputs) and checks its sends, timers, notes, random draws and the state digest after every step. Random values are answered from the log, so the node's use of its *streams* is checked by name and ordinal, not by recomputing the generator. Clock skew and `CONFIG_PATCH` are reproduced from the log; a node edited by a synthetic `PATCH_STATE` is refused. Timing of delivery, latencies and fault decisions are taken from the log as given, not checked. |
| DEV-33 | **Live local viewer (FR-50)** is read-only by design: it can browse, scrub, explain (`why`, `knows`) and compare, but cannot record, branch, intervene or delete (those stay in the CLI, so the web surface cannot change a timeline). It binds to 127.0.0.1 unless `--bind` says otherwise, serves one fixed page that loads no external resource, answers only for timelines in the store, and handles requests one at a time on the JDK HTTP server's dispatch thread. The diagram shows the first 5,000 events of a timeline (the response says `truncated` and the total; the world and causal-evidence endpoints work for every position, tested on a timeline of over 5,000 events); the page can highlight an event's causal past and its chains, with potential (OMISSION) links dashed and a note that the past is a set of suspects, not a proof. It is not a replacement for the HTML report, which stays the portable artefact (D-18). |
| DEV-34 | **Log compression (cut line 6) is opt-in gzip of event segments** (`--compress`; `NNNNNN.log.gz`, the same JSON lines, a sync flush after every step group so a crash loses at most the unfinished group). The reader handles both forms, in one store and in one branch lineage; a compressed segment cut at any byte is a torn tail, tested at every byte offset of a segment (NFR-11). Measured (B12, B6b): about 4.5x smaller (65 against 296 bytes per event on gossip), recording about 3.4x slower than plain (still far above the 20,000 events/s target), parsing about 1.25x slower. The log hash is unaffected (it is over events). **Not done:** the "difference from the previous local event" vector compression the specification mentions for Phase 16, because its trigger ("vector-clock cost dominates at 20 nodes") did not occur: B3 shows 158 bytes per event line and 95 ns per receive at 20 nodes. |
| DEV-35 | **Pinned continuation policy (D-15, Stretch) is an opt-in** (`--pinned`, recorded in the branch's header as the reserved parameter `chronos.continuation=pinned`). The specification calls its matching rules "complex" and does not define them, so this is a deliberately small definition: a message the parent also sent (same id, sender, receiver and type) is delivered at the instant the parent delivered it if that instant has not passed, otherwise and for new messages the policy falls back to Continue. Only the base delay is pinned (faults apply on top); randomness is identity-keyed already. Tested: a chain scenario where Continue and Pinned deliver at 25 and 20 respectively for a 5 ms delay and both at 35 for a 15 ms delay; every branch replays; a no-op branch reproduces the parent under either policy (M7); locality (M8) holds under Pinned. Continue stays the default, as D-15 decides. |
| DEV-36 | **Making law M10 hold.** Audit finding: M10 (the first causal divergence is the intervention's own event; every root of the branch lies in its causal future) failed for `REMOVE_FAULT` and, found later by sweeping the whole catalogue, for several other interventions. Fixes: (1) **root ordering**: at equal virtual time an `iv:` event comes before other roots (it is applied at the branch point, before the step that follows); (2) **ghost rules**: a removed rule stays in the injector as a ghost that still matches (partition windows, message rules, slow links, crash and pause windows, a removed restart that keeps a crash going, after-event rules) but does nothing, so the events it would have changed get a FAULT edge from the intervention; (3) **lane marks** for events displaced by a removed input or fault; (4) **window alterations** (DEV-43). The comparator also reports, as *displaced* rather than as roots, divergent events that are (a) only renumbered (same kind and payload at another position of the same node's lane in the other timeline: node-local ids are per-node counters), or (b) *absence* consequences: the event the other timeline had under the same id depended on a message or fault this timeline does not reproduce, or (c) the node's first different event after a message to it was dropped by a divergent event (*silence*). Displaced events keep their consequences in the divergence cone; (b) and (c) are potential links, labelled as such in the report. **Tested** (`M10CatalogueTest`): every intervention type on RE; removal of every rule of 60 random plans; 120 random interventions of every type at random boundaries of chaos runs (strict: no exception); all branches replay. **Measured residual:** at the time of DEV-36/43 a 4,000-seed run left 6 of 8,752; these were cleared by DEV-47 (see there). |
| DEV-37 | **A world cannot be restored inside the boot sequence.** Audit finding: the log commits one group per node start, so position 0 is a group boundary, and branching there (for example `--remove-input` with its default branch point) produced a branch whose events did not continue the parent's (a `CorruptLogException` on reading it). Branch points are now rounded down only to boundaries at or after the end of boot (`TimelineManager.bootEnd`, found from the causal structure: NODE_STARTED events and the effects of start handlers); an earlier request is refused with the reason. |
| DEV-38 | **`why` prints a "possible silence" section** (an extension; the specification does not define it). The specification links a fault to a *timer* that noticed the silence (D-23); a message that never arrives and that nothing waits for with a timer leaves no event in the causal past of the failure, so the certain chains cannot name the fault (found by the evaluation: 0 of 100 on the tutorial case). The new section lists, for each node an invariant read, the messages dropped on their way to it after the last write the violation depends on, with the fault that dropped each. It adds no edge, changes no clock or digest, and is labelled potential in the output. See `docs/EVALUATION.md`. |
| DEV-39 | **A world at a step boundary is identified by the time and step count of the last event, not by the live clock.** Audit finding (intervention fuzzer, nested branches): a step that records nothing (a fault that finds nothing to do, a held item) advances the engine's clock and step count, so a checkpoint taken after such a step carried a later time than the same boundary reached by replaying from the start; a branch created from the checkpoint then recorded its `INTERVENTION_APPLIED` event at a different time from the one its lineage replay reproduced (`mismatch at iv:z12: virtualTime expected 59 got 57`). Images now store the time and step count of the last event as `time`/`step`; the live values are stored as `liveTime`/`liveStep` only when they differ, and are taken back only by a full verification replay from a checkpoint (`resumeStopState`), which must end exactly where the original run ended. **Second part (fuzzer, seed 6716):** no checkpoint is taken after a step that recorded nothing, because such a checkpoint claims the previous boundary but its agenda lacks the item the silent step consumed (a restart rule for a node that is not down), which can still decide when a descendant run ends; `LawsTest.m5_everyCheckpointEquals...` compares every stored checkpoint with the world replayed from the start. |
| DEV-40 | **Swapping a message with itself is refused** (`SWAP_DELIVERIES` with equal ids used to schedule the message twice and produce a log with duplicate ids; found by the fuzzer). |
| DEV-41 | **A branch made at its parent's own branch point does not inherit the parent's interventions.** Audit finding (fuzzer, seed 5219 of 14,000): the lineage replay applied every ancestor's interventions at that ancestor's branch point, including those of a parent whose events (recorded after the branch point) are not in the grandchild's prefix, so the replay produced `iv:z2` where the recording had `iv:z12`. The replay now skips an ancestor whose successor in the lineage branches at the same position (`LawsTest.m6_aBranchMadeAtItsParentsOwnBranchPoint...`). |
| DEV-42 | **A damaged checkpoint is skipped, not trusted** (a checkpoint is a shortcut; the log can always be replayed from an earlier point): `checkpointAtOrBefore` falls back to the next older readable one or to the start, `TimelineStore.damagedCheckpoints` lists the damaged ones. A checkpoint with an unsupported format version is still refused with an explicit error. Tested with random byte damage to logs (plain and compressed), checkpoints and the index file (`CorruptionFuzzTest`): the store returns either a lossless prefix ending at a step boundary or refuses. |
| DEV-43 | **Intervention-moved fault windows and origin-marked events are linked to the intervention.** (1) A fault whose end an intervention moved (a heal shifted earlier or later, a restart that ends a crash, a removal of an active partition or pause) remembers the original end; a timer firing whose OMISSION edge exists in one run and not in the other because of that gets a FAULT edge from the intervention, and so does a delivery that the original run would still have dropped. (2) The original delivery of a message an intervention duplicated carries the intervention's origin (part of its content digest) and now also its FAULT edge. (3) A handler's use of a patched configuration key or a reseeded stream (DEV-29). Each of these closed a root that M10 said must not exist; `M10CatalogueTest.m10RegressionsFoundBySweepingTheCatalogue` fails without them. |
| DEV-44 | **Systematic explorer (extension, not in the specification).** It enumerates every subset of at most K declared candidate faults in a fixed order (size, then candidate index) and runs each deterministically in memory; candidates are given with `--candidate SPEC` or generated from the scenario's fault-free behaviour (crash and pause of every node at grid times, partition of every pair that exchanged messages, drop of the first N messages of every observed link). Reductions, all reported: **trace equivalence** (identical sequences of event content digests are one execution, so rules that never fire are recognised as no-ops) and **superset pruning** of violating schedules (sound for minimal counterexamples only; `--no-prune` disables it). **Limits:** `--max-cases` bounds subsets processed (including duplicate traces and supersets skipped by pruning), and the report says how many schedules of the bound were not explored. This also bounds enumeration work when a large search space is mostly pruned; wall-clock limits are deliberately absent because they would make the exploration non-deterministic. It is not a model checker: it explores fault schedules of one seed, not message interleavings, and it claims nothing outside the bound. |
| DEV-45 | **Incident bundles (extension).** One ZIP (fixed entry timestamps, so the same incident gives the same bytes) with a checksummed manifest (format version, tool, scenario, parameters, seed, code version and fingerprint, event count, log hash, a SHA-256 and size for every file), the headers, summaries and event logs of the timeline and all its ancestors, `evidence.json` (violation, `why` chains, fault plan, interventions) and reproduction steps. Checkpoints and indexes are not bundled (derived). Import validates in a staging directory first (names, limits, checksums, headers, the log's own commit checksums, counts, log hash, and the causal evidence recomputed from the events) and moves the timelines into the store only if everything holds; an existing timeline with the same id must be identical. Reproduction replays through the lineage and, for a root timeline, re-executes the recorded scenario, seed and plan from scratch. **Boundaries:** reproduction needs the same scenario registered under the same name (a different class fingerprint is a warning); format version 1 is read only by tools that know it; the bundle carries no secrets beyond the trace, so it contains whatever the application put in its events and state. |
| DEV-46 | **Every reader of stored data refuses a malformed document with an `IllegalArgumentException`, never a raw runtime error.** Found by `ParserRobustnessTest` (structural and character-level mutation of headers, summaries, fault rules, interventions, events and world images): a field of the wrong type (for example `eventCount` as a list) escaped as a `ClassCastException`, which would have crashed an import of a forged-but-checksummed bundle or a hand-edited store. The six `fromMap` readers in the model module now convert such failures into `IllegalArgumentException("malformed X: ...")`; the store and the bundle importer already turn that into `CorruptLogException` / `BundleException`. |
| DEV-47 | **Races decided the other way are explained, as potential links, not reported as independent roots.** Audit finding (the review's six seeds 281, 552, 1945, 2696, 2715, 3079, then 4085, 8184, 9356, 10130, 22656, 23754 from wider sweeps): a branch root such as a `TIMER_FIRED` on a node whose counterpart in the baseline was a `NODE_CRASHED`, a delivery or an event with an OMISSION edge. Traced in the event graphs, none was a runtime defect: an intervention (`DROP_MESSAGE` on a receiver's lane, `CONFIG_PATCH` of a heartbeat, `DELAY_MESSAGE`, `REMOVE_INPUT`) moved something the baseline's event depended on **in time only** (a crash-after trigger named by a node-local id that now refers to a later event; a heartbeat that now arrives after the watchdog; a delivery postponed past a timer), so a race between two events of the same instant or the same window was won by the other one. The structural digest ignores timing fields, so the shifted event compares SAME and the existing absence rule (which needs a missing or changed cause) could not see it. `TimelineComparator.demoteShiftedCauses` now demotes such a root to *displaced* (reason `timing`) when the event it replaces in the other timeline (1) depended, through a MESSAGE, FAULT or OMISSION edge, on an event that exists here at a different strict-digest time, (2) is found here later under another id, or (3) handled a message whose fate here (delayed, dropped) is recorded in an event, **and** that event lies in the causal future of another root or of an already displaced event of the same timeline. The absence rule now also considers OMISSION parents (a fault absent here that the baseline's timer had noted). Displaced events keep their consequences in the cone, and remain labelled *potential*: the report says the race was decided the other way, which the times show, but it is a statement about two timelines, not an edge the engine recorded. No engine behaviour, clock, id or digest changed. **Limit:** a root is explained only if some other root precedes it causally, so a root that has no such predecessor is still reported as a root; the 30,000-seed sweep (66,427 comparisons, 13 intervention types, `CHRONOS_M10_SEEDS=30000`) found none outside, but a sweep cannot prove there is none. Tests: `M10CatalogueTest.m10HoldsForTheSeedsWhoseRaceWasDecidedTheOtherWayByTheIntervention` fails without the change (checked) and passes with it. |
| DEV-48 | **Failure minimization (extension, not in the specification).** `chronos minimize <timeline>` re-executes a root timeline's scenario, seed and fault plan (never a branch: its failure may come from its interventions) under smaller plans: Zeller's ddmin over the rules, then a binary search for smaller `duration` / `by` values, then the shortest horizon that still reaches the violation. A candidate counts only if it violates **the same invariant** (a different failure is a different bug; the demo scenarios each have one invariant, so no test distinguishes this rule from "any violation" yet). Every candidate is a complete deterministic re-run from scratch, cached by its canonical plan and counted; `--max-runs` bounds them and a run that hits the bound is reported "NOT FINISHED" (exit code 3). The result is checked to be **1-minimal** by re-running it without each kept rule, and those runs are printed. **Limits:** 1-minimal is not minimum-cardinality; a parameter's binary search assumes failure is monotone in it, and only values that were actually executed are accepted, so the value is "the smallest tried that fails"; removing a fault never changes what another fault does here (identity-keyed randomness), which is why re-execution is sound, but a plan with `nonLocal` rules is minimized the same way and its report carries no locality claim. `--save` records the result with `Counterexample.saveRun` (the same checksummed, re-executable document the explorer writes, plus a `minimization` section). Tests: `FailureMinimizerTest`. |
| DEV-49 | **Three defects found by `chronos check` and by running it over every store the fuzzers write.** (a) *A branch's summary carried the hash of empty input as its log hash.* `Recorder.switchTo` reset the hash but left hashing switched off from the replay that builds the branch's world, so `summary.logHash` of every branch was `e3b0c442...`; it now hashes the branch's own events (those after its branch point), and `chronos check` accepts the old value for a branch, with a warning, because stores written earlier have it (a root with that value is a failure). Test: `StoreCheckerTest.aHealthyStorePassesEveryCheck...`, which fails without the fix. (b) *A run or branch that was refused after its writer was opened left debris.* `branch T0 --crash ghost:5` printed the error and left `T0.1  RECORDING?` in `chronos ls` and in the catalogue (the same for `run --fault crash:zz:5`); the next branch then became `T0.2`. `Recording.record` and `TimelineManager.branchAs` now call `TimelineStore.discardUnfinished`, which removes only a timeline that has no summary and no children, and releases the reserved id. A process kill cannot run it; `chronos check` reports that leftover as a warning with its cause (`PersistenceTest.aProcessKilledMidWrite...`). Test: `RefusedRunCleanupTest`. (c) *A negative horizon was accepted* by `run`, `branch --horizon`, `explore` and `campaign` and silently produced a run that ended at once; it is now refused with a message. |
| DEV-50 | **Whole-store integrity check, `chronos check [timeline]... [--no-replay] [--json] [--strict]` (extension).** Read-only. ## Simplifications (SIMPLIFIED in the traceability matrix)

| ID | What is simplified |
|---|---|
| DEV-15 | World images (checkpoints) are canonical JSON trees built by the runtime (`WorldImage` holds an opaque map), not typed record hierarchies. Completeness is enforced by law M5, tested at every checkpoint of every demo. |
| DEV-16 | **Indexes (FR-18) are persisted** under `index/main.idx` when a timeline finishes (binary: node lanes, kind lanes and a virtual-time sample table as delta-varints, with a CRC-32), and loaded with a validity check (format, event count, first and last event id, checksum, a sample of entries against the log). A missing or suspect file is rebuilt from the log in memory; reading never rewrites it (NFR-04); `chronos reindex` repairs the files. What is NOT stored: byte offsets into the log segments, because the store loads a whole timeline into memory. **Measured honestly (B6b):** loading the persisted indexes (0.8 ms at 20,000 events) is about as fast as rebuilding them (1.0 ms); the cost of opening a timeline is parsing the log (62 ms), which the index does not avoid. The files satisfy the specification's storage layout and its rebuild rule; they are not a performance feature. A branch's index covers the parent's prefix by cutting the parent's index at the branch point. |
| DEV-17 | Stepped replay with breakpoints (R3/FR-24) is `ReplayEngine.runUntil` and the session command `run-to` (breakpoints on an event kind, node, text, virtual time or the violation); there is no separate stepping UI. |
| DEV-18 | The HTML report draws at most the first 600 events in the SVG diagram and 3,000 table rows. |
| DEV-19 | `maxFirings` on fault rules is validated (allowed only on time-triggered rules) but time-triggered rules fire once, so it is not enforced as a counter. |
| DEV-20 | Persisted storage uses one writer thread per recording and fsync-free flushes per step group: a crashed *process* leaves a readable log (tested by killing a real process); durability against power loss is not claimed. |

## Known limitations of what *is* implemented

* **Roots from the baseline.** In a baseline-versus-branch comparison the baseline-side roots (for example the watchdog that fired
  only in the baseline) are baseline events the intervention replaced; M10's "every root lies in the intervention's causal future"
  is tested for the roots *in the branch* (DEV-36 and DEV-43 describe the links added and the measured residual).
* **A baseline that stops at its first violation** (the default `stopOnViolation`) ends earlier than the branch, so the branch's
  tail appears as `Extra` roots ("one timeline ends earlier", Section 20). The demo records its baseline with `--no-stop`.
* **Wall-clock numbers** in `docs/BENCHMARKS.md` come from one machine (Apple M2 Max, JDK 21).
* **Evaluation is not blind** (`docs/EVALUATION.md`).
